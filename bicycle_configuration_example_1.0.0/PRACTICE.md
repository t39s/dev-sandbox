# Практикум: ветки, PR и конфигурации

## Как выполнить процесс в GitHub

Для настоящей команды достаточно одного репозитория и ветки `main`. Минимальные правила ниже являются договорённостью команды. Их можно поддержать доступными настройками репозитория; в этом комплекте настройки GitHub не применялись.

1. От согласованного состояния создать ветку изменения, например `topic/04-brakes`. Изменить описание узла и приложить свидетельства исследования. Не создавать ветку для каждой идеи, которую достаточно сравнить в таблице.
2. Открыть Pull Request: базовая ветка `main`, ветка предложения `topic/04-brakes`. Заполнить пять вопросов [шаблона](snapshot/.github/pull_request_template.md): вопрос, альтернативы, последствия, проверка, решение.
3. Другой участник просматривает **Files changed** и основания выбора, затем оставляет замечания или одобрение. Проверяет не только текст, но и зависимые узлы. Для PR-04A это колёса, рама и тормозные ручки. Механизм описан в [Reviewing proposed changes](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/reviewing-proposed-changes-in-a-pull-request).
4. Автор исправляет ту же ветку. Перед окончательным принятием учитывает актуальную базовую ветку и параллельные изменения. После существенного исправления проверяющий повторяет затронутую проверку.
5. Принимающий участник объединяет PR в `main` либо закрывает с причиной отказа. Одобрение и слияние — отдельные действия. Для наглядности в приложенном Git использованы merge commits. См. [Merging a pull request](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/merging-a-pull-request).
6. Когда нужен выпуск для изготовления, команда принимает конкретный состав и условия применения, фиксирует решение в `release.md`, создаёт аннотированный тег и сохраняет SHA commit. На компьютере выполняют, например, `git tag -a baseline-v1 -m "B1: prototype authorized"` **только находясь на уже выбранном commit**. В комплекте тег уже создан.
7. После реальной сборки или обслуживания отдельно обновляют запись экземпляра. Принятие проектного PR не заполняет эту запись автоматически.

Это адаптация [GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow); выбор базовой и предлагаемой веток описан в [Creating a pull request](https://docs.github.com/articles/creating-a-pull-request), режимы тегов — в [git-tag](https://git-scm.com/docs/git-tag).

В обычной работе завершённые ветки можно удалять. Здесь они оставлены для обучения. Issue полезен, если наблюдение нужно отложить и вести отдельно; для немедленно разбираемого изменения достаточно PR и ссылки на свидетельство. Нет обязательного проекта задач, отдельного ADR или согласующего комитета.

## Посмотреть локальную историю

Откройте терминал в каталоге распакованного комплекта. Команды не обращаются в интернет и ничего не публикуют.

```bash
git clone bicycle-demo.bundle demo
cd demo
git log --all --graph --oneline --decorate
git branch -a
git tag
```

`demo` — ваш рабочий клон; `snapshot` остаётся готовой копией последнего согласованного состояния. После клонирования учебные ветки видны как `origin/topic/...`; здесь `origin` указывает на локальный bundle.

### 1. Найдите конкретный состав B1

```bash
git rev-parse baseline-v1^{commit}
git show baseline-v1:release.md
git show baseline-v1:config/drivetrain.json
```

Сверьте SHA с `COMMITS.json`. Прочитайте границу разрешения: один опытный экземпляр и контролируемые пробы. Пригодность для обычной эксплуатации на этом этапе не подтверждена.

### 2. Сравните проект до и после доработки

```bash
git diff baseline-v1 baseline-v2 -- config/drivetrain.json
git show origin/alternative/05-small-ring:config/drivetrain.json
git show origin/alternative/05-small-ring:evidence/E05-rejected.md
```

Назовите не только числа зубьев, но и появившийся передний механизм переключения. Объясните, почему отклонённая ветка не должна попасть в `main`.

### 3. Найдите момент расхождения проекта и физического экземпляра

```bash
git show baseline-v2:config/drivetrain.json
git show baseline-v2:units/BUD-001.json
git show unit-serviced:units/BUD-001.json
```

В первом файле уже `DRIVE-2-SIM`, во втором ещё `DRIVE-1-SIM`. Только третья команда показывает зарегистрированную установку нового комплекта. Раздел `as_built` сохраняет прежний состав и DEV-01.

### 4. Проверьте всё автоматически

Вернитесь в каталог комплекта:

```bash
cd ..
python verify.py
```

Проверка клонирует bundle во временный каталог, воспроизводит слияние несовместимых колёс и тормозов, подтверждает отсутствие текстовых конфликтов и выявляет обе ошибки интерфейсов. Затем проверяет исправленные версии, отказ от альтернативы, бюджет, передаточные отношения, сохранность исходной записи экземпляра и совпадение snapshot с `main`. Ваш клон `demo` не меняется.

Успешный результат относится к проверяемым свойствам учебного материала. Флаг согласованности вымышленных комплектов не заменяет проверку реальных компонентов и испытания.

## Вопросы для разбора

1. Почему PR-03 можно принять, хотя подъём с грузом ещё не проверен?
2. Почему экономия пяти единиц в PR-04B потребовала проверки двух узлов?
3. Почему нельзя отправить сборщику только ссылку на `main` и считать состав зафиксированным?
4. Почему `git revert` изменения трансмиссии не восстановит старую трансмиссию на велосипеде?
5. Как узнать, какой звонок стоит на BUD-001 после обновления проекта до B2?
6. Когда команда может обоснованно закончить работу над исходной задачей?

## Ответы

1. Решение ограничено опытной конфигурацией; открытая гипотеза и обязательная проба явно записаны. Это не окончательное принятие пригодности велосипеда.
2. Ротор и втулка соединяются через интерфейс. Изменение цены колеса одновременно изменило этот интерфейс; проверять надо комбинацию переднего и заднего узлов.
3. `main` меняется. Нужны определённый commit, состав в нём и решение о разрешённом применении. Имя принятого тега удобно, но команда сохраняет точный SHA и не переносит тег на другой commit.
4. Git изменит описание. Для физического возврата нужны отдельная работа, проверка и запись об экземпляре. Старые commits при этом остаются источником исходных данных.
5. Прочитать актуальную запись экземпляра: BELL-B-SIM, отклонение DEV-01 сохранено. По одной проектной B2 можно ошибочно ожидать BELL-A-SIM.
6. После выполненной модификации, повторной проверки исходного маршрута и актуализации конфигурации экземпляра — при отсутствии значимого разрыва в исходной цели. В рассказе результаты проб условны; учебный материал завершается по собственным критериям из постановки.
